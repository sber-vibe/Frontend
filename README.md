# Frontend — рабочее место специалиста по проверке субсидий

Кейс «Автоматическая проверка пакета документов на получение субсидии» (СберБизнесВайб).
Next.js 16 (App Router) · TypeScript · SCSS-модули · framer-motion · Vitest · Playwright.

![Итог проверки](docs/screenshots/desktop-05-result-incomplete.png)

## Экраны

| Экран | Путь | Что умеет |
|---|---|---|
| Вход | `/login` | Keycloak OIDC (Authorization Code + PKCE). Демо-вход с выбором роли — только при `NEXT_PUBLIC_DEMO_LOGIN=true` |
| Дашборд | `/checks` | Сводка и фильтры «Ожидают / Есть ошибки / Требуют внимания / Пройдены / Решение принято», поиск, частые замечания по потоку, документы с истекающим сроком |
| Новая проверка | `/checks/new` | Организация, ИНН, сумма и программа субсидии (или «определить из заявления»), перечень документов программы |
| Пакет документов | `/checks/:id` | Загрузка нескольких файлов (PDF, DOC/DOCX, XLS/XLSX, JPG/PNG), этапы фоновой обработки по каждому файлу, оригинал рядом с разбором, тип + уверенность + поля с фрагментом источника, правка типа и полей (видна как действие специалиста), повтор обработки после ошибки модели, предупреждение о повторном пакете |
| Итог проверки | `/checks/:id/result` | Пройдено / требует внимания / есть ошибки; комплектность с обязательными, условными и лишними документами и кнопкой «Дослать»; замечания со ссылкой на оригинал; решение специалиста (принять / вернуть / отклонить); протокол для заявителя, печать |
| Журнал проверки | `/checks/:id/journal` | Кто, когда и что сделал: специалист, модель, правила; отказы с причиной |
| История организации | `/organizations/:inn` | Все проверки по ИНН, замечания и решения |
| Администрирование | `/admin` | Роль `admin`: программы субсидий и перечни документов, правила проверки и их параметры, общий журнал — без правки кода |

Интерфейс рассчитан на компьютер специалиста и администратора и не ломается на телефоне.
Контракт API со всеми полями и маршрутами: [docs/API_CONTRACT.md](docs/API_CONTRACT.md).

## Главный принцип: правила только на сервере

Фронтенд **не** вычисляет комплектность, корректность документов, арифметику и итоговый статус.
Всё это приходит из backend (`report.status`, `report.findings`). На клиенте только:

- проверка ввода в формах (формат ИНН, сумма > 0, расширение/размер файла) — для удобства, сервер проверяет повторно;
- отображение: подписи типов, цвета статусов, группировка замечаний.
  Если сервер присылает `severity`, используется он; иначе уровень берётся по известному коду замечания.

Порог `NEXT_PUBLIC_CONFIDENCE_THRESHOLD` влияет только на то, показывать ли пометку
«Тип документа требует подтверждения специалиста»; сам тип и confidence определяет модель на сервере.
Сводки дашборда (частые замечания, сроки документов) только группируют замечания из отчётов сервера.
Роли из токена влияют только на показ меню: доступ к API проверяет backend.

## Запуск

Нужен Node.js ≥ 20.9 и запущенный backend (по умолчанию `http://localhost:8080`).

```sh
cp .env.example .env.local   # при необходимости поправить BACKEND_URL
npm ci
npm run dev                  # http://localhost:3000
```

Prod-сборка: `npm run build && npm start`. Docker:

```sh
docker build -t subsidy-frontend --build-arg BACKEND_URL=http://backend:8080 .
docker run --rm -p 3000:3000 subsidy-frontend
```

Весь стенд (nginx + frontend + backend) поднимается из репозитория [sber-vibe/infra](https://github.com/sber-vibe/infra).

Next.js проксирует `/api/*` на `BACKEND_URL` (rewrites), поэтому CORS на backend не нужен.
Адрес фиксируется при сборке.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BACKEND_URL` | `http://localhost:8080` | Куда проксировать `/api/*` |
| `NEXT_PUBLIC_AUTO_CLASSIFY` | `false` | `true` — тип документа определяет backend по содержимому, при загрузке `type` не отправляется. `false` — специалист выбирает тип (контракт текущей Java-заготовки) |
| `NEXT_PUBLIC_CONFIDENCE_THRESHOLD` | `0.8` | Ниже этого порога тип помечается как требующий подтверждения |
| `NEXT_PUBLIC_POLL_INTERVAL_MS` | `2000` | Период опроса сервера, пока документы обрабатываются в фоне |
| `NEXT_PUBLIC_OIDC_ISSUER`, `NEXT_PUBLIC_OIDC_CLIENT_ID` | пусто | Keycloak realm и public client. Redirect URI: `<origin>/auth/callback` |
| `NEXT_PUBLIC_DEMO_LOGIN` | `false` | Только для разработки и e2e без Keycloak: вход по имени с выбором роли. Роль не даёт прав на сервере. В сдаваемой сборке — `false` |

## Контракт API

Используется `/api/v1` backend. Текущая Java-заготовка поддерживает `document-types`, `applications`, `documents`
(upload / download / delete) и `check`; остальное фронт уже умеет показывать и описывает в
[docs/API_CONTRACT.md](docs/API_CONTRACT.md): программы, фоновая обработка, комплектность с условными документами,
решение специалиста, журнал, администрирование.

Если маршрута на сервере ещё нет (`404 No static resource`, `405`, `501`), интерфейс пишет
«сервер пока не поддерживает …» и не подставляет придуманные данные.
Пока backend отвечает на PATCH `405`, правка типа работает через перезагрузку того же файла
с новым типом и удаление старой записи. Заголовок `Authorization: Bearer …` отправляется, если специалист вошёл через Keycloak.

## Тесты

```sh
npm run typecheck
npm test            # Vitest + Testing Library: API-клиент, формы, программа, загрузка, фоновая обработка, правка, итог, решение, журнал, админка, протокол
npm run e2e         # Playwright: полный сценарий специалиста на десктопе и телефоне против живого backend
                    # (сборка без Keycloak: NEXT_PUBLIC_DEMO_LOGIN=true npm run build)
```

E2E ожидает запущенный backend. `PW_CHANNEL=msedge` или `PW_CHANNEL=chrome` использует установленный браузер вместо скачанного Chromium.
Скриншоты прогона сохраняются в `docs/screenshots/`.

## Структура

```
src/
  app/                    маршруты (login, auth/callback, (workspace)/checks/…)
  components/
    ui/                   UI-кит: Button, TextField, Badge, Toast, Dialog, ProgressRing…
    checks/               дашборд и форма новой проверки
    package/              загрузка, список, просмотр оригинала, разбор документа
    report/               итог проверки и решение специалиста
    journal/              журнал действий
    admin/                программы субсидий и правила
  lib/                    api, типы, auth/OIDC, форматирование, валидация, представление статусов, протокол
  styles/_tokens.scss     брейкпоинты и миксины; цвета задаются CSS-переменными в globals.scss
e2e/                      Playwright-сценарии
```
